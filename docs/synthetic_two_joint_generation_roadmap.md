## 1. 背景・目的

`docs/fable5_progress_to_constraint_point_generation.md` の到達点は「入力中立面点群がある場合のanchored scaffold配置」であり、「拘束点のみからの生成」は未解決。`docs/fable5_alternative_generation_paradigms.md` は「65パーツでは生成は原理的に成立しない」「モデルより先に学習不要で作れる教師データ・中間表現を整備すべき」と結論づけている。

本ロードマップは、その結論の実行フェーズとして、**締結点2点の板金部品をCATIA上でルールベースに大量合成し、拘束点条件付き生成モデルの教師データを拡充する**ことを目的とする。

段階的ロードマップの第一段として締結点2点を選ぶ理由:

1. 締結点数が最少に近く、拘束点だけでは形状の自由度が最も大きい(=モデルにとって最も難しく、最も生成多様性を要求されるケース)。
2. 締結点2点は「強度部品」に限らない(ブラケット、カバー、スペーサー、センサー台座など機能クラスが多様)ため、ルールベース生成エンジンを分岐させる必要がある。
3. 強度部品であっても、剛性を高めるべき方向は拘束点だけからは一意に決まらない。この不定性自体を、同一拘束点配置に対する**複数の妥当形状のバリエーション**として教師データに埋め込む(`fable5_progress_to_constraint_point_generation.md` §6.3 の「多様性を失わずに板金らしい形状制約を入れる」という未解決課題への直接的な回答になる)。

|---|---:|---:|---:|---:|---:|
| A0072600002 | 43 | 0 | 1 | **0** | 42 |

## 3. Configuration分類(確定: 法線関係 + 同一平面判定)

`joints.json` の `axis.direction_xyz` (締結軸=板厚方向)を使い、2点の締結軸ベクトルのなす角(内積 `d`)で一次分類する。さらに、法線が同方向の場合のみ**同一平面判定**を行い、非強度部品はこのケースに限定する。

「強度部品でないのは締結点が同一平面に存在する場合だけ」という条件は、法線が異なる3クラス(`parallel_opposite`/`orthogonal`/`oblique`)は定義上どこかに曲げ・オフセットが入る(=2点は同一面上にありえない)ため、常に強度部品になることを意味する。同一平面判定が意味を持つのは法線が同方向の場合のみ。

| class | 判定条件 | 想定形状 | 剛性強化(§4) |
|---|---|---|---|
| `coplanar_flat` | `d > 0.9` かつ `\|(p2−p1)・n1\| < 1.0mm` | 同一平面上のカバー/スペーサー/平板ブラケット | **スキップ(非強度部品)** |
| `parallel_same_offset` | `d > 0.9` かつオフセットあり(段差・ジョグ) | オフセットブラケット | 適用 |
| `parallel_opposite` | `d < -0.9` | 対向面(両面挟み込み)。スペーサー、対向ブラケット | 適用 |
| `orthogonal` | `-0.15 < d < 0.15` | L字/コーナーブラケット。曲げ1回で2面をまたぐ | 適用 |
| `oblique` | 上記いずれにも該当しない(`0.15 <= |d| <= 0.9`) | 自由曲面追従パネル、任意角度フランジ | 適用 |

### 3.1 実データによる閾値検証(完了)

3アセンブリの3点以上締結部品から2点部分集合を全組(31,846組)抽出し、法線内積とオフセットの分布を確認した。

**法線内積のヒストグラム**(±0.05刻み、境界付近):

```text
[-1.00, -0.95): 4525   ← parallel_opposite の芯(ほぼ完全反平行)
[-0.95, -0.80): 1379   境界域
[-0.80, -0.15): 2065   oblique域
[-0.15,  0.15): 9408   ← orthogonal の芯(designが90°基準で作られているため最大クラスタ)
[ 0.15,  0.80): 2998   oblique域
[ 0.80,  0.95): 2375   境界域
[ 0.95,  1.00): 8876   ← parallel_same の芯(ほぼ完全平行)
```

`orthogonal`域(-0.15〜0.15)と`parallel_*`域(±0.95以上)にはっきりしたピークがあり、実部品はCAD設計上0°/90°/180°を基準に作られていることが裏付けられた。**閾値0.9 / 0.15は妥当と確認**(0.8〜0.95の境界域がやや厚いため、Phase 2でクラス間の漏れが問題になった場合は0.95へ引き締める余地を残す)。

**同一平面判定のオフセット許容量**: `parallel_same`(d>0.9)の9,956組についてオフセット`|(p2−p1)・n1|`の分布を細かく見ると、

```text
[ 0.0,  0.5) mm: 1871  ← 真の同一平面クラスタ(スパイク)
[ 0.5,  1.0) mm:  327
[ 1.0,  2.0) mm:  776
[ 2.0,  3.0) mm:  618  ← ここから先はなだらかな連続分布(段差形状の自然な広がり)
...
```

0〜0.5mmに明確なスパイクがあり、1mmを超えると分布はなだらかな連続(段差ブラケットの自然なばらつき)に移行する。データセットの板厚が1.3〜2.4mmであることも踏まえ、**`coplanar_flat`判定のオフセット許容量は1.0mm(板厚未満)に確定**する。

共通パラメータ(全クラス): 締結点1/2の座標、板厚、締結点タイプ(bolt/mounting_hole/weld)、座面径。`coplanar_flat`はこれと外形輪郭パラメータのみで完結し、§4の補強構造パラメータは持たない。

## 4. 剛性強化方向と構造補強(強度部品のみ)

### 4.1 設計方針(BIW実務知見を反映)

ユーザー知見: 自動車板金部品では**フランジが圧倒的多数**、リブはほとんど使われず、フランジの時点でボスが併用される。ボスとフランジの境界は実務上曖昧。これを踏まえ、独立した3フィーチャー(rib/flange/boss)をランダム選択する設計ではなく、次の構造にする。

- **フランジを主構造とする。** 強度部品クラス(`coplanar_flat`以外の4クラス)は必ずフランジ補強を持つ。
- **ボスを独立フィーチャーにしない。** 締結点近傍でのフランジ幅のローカルな膨らみ(パッド状の幅変調)として表現し、ボス/フランジの境界の曖昧さを設計にそのまま反映する。
- **ビードはフランジと並ぶもう一つの主要な補強手段。** ただし幾何的に別種のフィーチャー(境界エッジの曲げではなく、一般面上に入れる線状の押し出し/プレス形状)なので、フランジと同じ生成ロジックには混ぜず、独立した生成エンジンとして§4.4で扱う。Phase 1のスコープには含めない(later)。

### 4.2 パラメータ化

- `reinforcement_direction` (θ): ローカル接平面内の角度。2点を結ぶ線を基準0°とする。フランジを立てる境界辺の選択・向きを決める。
- `flange_width_profile`: 基本幅 + 締結点ごとのローカル膨らみ(振幅・位置・R)。膨らみ振幅が小さければ「均一フランジ」、大きければ「フランジ+ボス的パッド」に自然に連続する。
- `flange_height`: 板厚tに対する比率でランダムサンプリング(例: 高さ3〜8×t)。
- `flange_angle`(曲げ角度、訂正済み): **既定値は90°**(フランジは90°で立てるのが基本、というユーザー訂正を反映)。90°以外に立てる斜めフランジは稀なケースとして低確率でサンプリングする(高確率で90°、低確率で90°以外の角度)。
- `return_flange`(戻りフランジ、新規): `flange_angle`が90°以外になった稀なケースでのみ有効化する。斜めフランジの先端に、一般面と平行なもう一つのフランジを追加する(ユーザー訂正: 「フランジを斜めに立てる場合は、その先に一般面と平行なもう一つのフランジが斜めフランジの端に作られることが多い」)。パラメータ: `return_flange_length`(板厚tに対する比率)。90°フランジの場合は通常不要(`return_flange_enabled=False`が既定)。
- `corner_radius_mm`(コーナーR、確定): フランジ輪郭の外側コーナーに適用する丸め半径。**最小値=外R5mm**(ユーザー製造制約)を下限としてサンプリング。CATIA側実装は§5の`AddNewCorner`/`AddNew3DCorner`を参照。
- `bend_radius_mm`(曲げ半径、**未確定**): ベースパッチとフランジの境界(折り目)に入れるフィレット半径。コーナーR(輪郭の丸め)とは別物で、板厚tに対する比率(一般的な板金設計則では1〜2×t程度)で扱う想定だが、ユーザーからの指定がまだないため§9の未決事項として残す。
- `general_face_bend_angle`(一般面の曲げ角度、**確認済み**): フランジ(edge機能)ではなく、`orthogonal`/`oblique`クラスで2締結点の非同一平面をつなぐ**ベース中立面自体**の折れに関わるパラメータ。単発の曲げで測定済みの全体角度(2点の法線がなす角)を一気に処理するのではなく、**1回あたりの曲げは45°を推奨値**とし、必要な全体角度を複数ファセットに分割して段階的に折る。板厚保護・スプリングバック抑制という一般的な板金設計則に沿う。個々の曲げの絶対上限は90°(フランジと共通の製造制約)。ファセット数は全体角度から決定論的に導出できる(例: `orthogonal`の全体角度≈90° → 2ファセット×45°)。ファセット境界の位置(2点を結ぶパスのどこで折るか)には自由度が残るため、これを追加のランダムサンプリングパラメータとして多様性に使える。

ビード(ビード補強)は§4.4で別エンジンとして扱う(rib/低確率オプションという旧フレーミングは撤回)。

### 4.3 力学的対応関係

| 構造要素 | 効く方向 | 配置ルール |
|---|---|---|
| フランジ | θと直交するエッジに立てると、θ方向まわりの曲げに対する断面係数を稼ぐ(チャンネル梁のフランジと同じ原理) | 境界辺のうちθと最も直交する辺を選択 |
| フランジ幅のローカル膨らみ(ボス相当) | 方向非依存。締結点周りの引きちぎれ・座屈耐性 | 締結点近傍でのみ幅を増やす |
| 戻りフランジ(斜めフランジ時のみ) | 先端を一般面と平行に戻すことで、開放端の座屈・変形を抑える | `flange_angle`が90°以外の稀ケースでのみ追加 |

ビード(線状プレス補強)は幾何・力学モデルが上記フランジ系とは別種のため§4.4で扱う。

### 4.4 ビード補強エンジン(将来実装、Phase 1スコープ外)

ユーザー知見: 実務ではフランジではなくビードで補強することも多い。フランジ生成エンジンとは別に、ビード生成エンジンを用意する方針とする。

現時点でのスコープ整理(詳細設計は着手時に別途行う):

- ビードは一般面(境界ではなく面の内部)に入れる線状の押し出し/プレス形状であり、境界エッジを曲げるフランジとは幾何的に異なるプリミティブが必要。
- 力学的には、ビード方向と**直交する軸まわりの曲げ**に効く(§4.3のフランジとは効く方向の考え方が異なる)。
- GSD実装は§5のフランジ用マッピング(Sweep/Fillet/Corner中心)をそのまま流用できない可能性が高く、着手時に別途CATIA V5 Automationを調査する。
- ロードマップ上の位置づけ: Phase 3以降でフランジ主体の生成が効果検証(§7 Phase2ゲート)を通過した後に、フランジと並ぶ第二の補強エンジンとして着手する。

## 5. 実装方針(確定: GSDで中立面を直接作成)

ソリッドモデリング(Sheet Metal Design工程)を経由せず、GSD(サーフェス)で中立面を直接作成する。これにより:

- `_archive_pre_annotation_tool/fable/catia_midsurface.py` が抱えていた「フランジ追加時の面積ヒューリスティック誤判定リスク」(既存ガイド`catia_midsurface_guide.md`§7に明記)は**そもそも発生しない**。ソリッドから面を抽出する工程自体が存在しないため。
- 板厚は生成時に付与するスカラー属性として一貫性を保証する(既存スクリプトのようなt/2オフセット距離の実測検証は不要。その代わり、生成した中立面ジオメトリ自体が自己交差・法線不整合を起こしていないかの独自チェックが必要になる。§7参照)。
- `catia_midsurface.py`は実部品からの中立面抽出という既存用途では引き続き使うが、合成生成パイプラインでは**再利用しない**(§4の旧版から方針変更)。

再利用するのは以下:

- `Dispatch("CATIA.Application")` + `DisplayFileAlerts = False` のバッチ制御パターン
- `PasteSpecial` によるSTP出力パターン
- `annotation_tool.schema` の `AnnotationDocument` / `Joint` / `Axis` / `PartRef` — 生成パラメータから直接`joints.json`を書き出せる(人手アノテーションと異なり真値が既知なので自動生成できる)

新規モジュール案(`AutoMetalSheet`直下に新規パッケージ、既存の`cae_mesh_generator` / `annotation_tool`と並列):

```text
synthetic_generator/
  src/synthetic_generator/
    classify.py          # 2点の軸方向+オフセットから configuration class (5種)を判定
    templates/
      coplanar_flat.py
      parallel_same_offset.py
      parallel_opposite.py
      orthogonal.py
      oblique.py
    reinforcement.py      # reinforcement_direction, flange_width_profile, rib有無のサンプリング
    gsd_build.py          # configuration + パラメータ -> CATIA COM(GSD)呼び出しで中立面サーフェス構築
    annotate.py           # 生成パラメータ -> joints.json (annotation_tool.schema を再利用)
    batch_generate.py     # パラメータをランダム/グリッドサンプリングして一括生成
  tests/
```

### 5.1 GSD API マッピング(調査完了)

CATIA V5 Automation公式ドキュメント(https://catiadesign.org/_doc/V5Automation/ 、`GSMInterfaces.HybridShapeFactory`)を調査し、以下のマッピングを確定した。

| 生成要素 | 使用するHybridShapeFactoryメソッド | 用途 |
|---|---|---|
| ベース中立面パッチ | `AddNewFill` | 2締結点周りの境界ワイヤーフレームからベースパッチを生成 |
| フランジ(曲げ部サーフェス) | `AddNewSweepLine` | ガイド=ベースパッチの境界エッジ、プロファイル=`flange_angle`で傾けた線分。線形プロファイルのスイープでフランジ面を生成 |
| フランジ輪郭の外側コーナー丸め | `AddNewCorner` / `AddNew3DCorner` | スイープ前のワイヤーフレーム(境界ポリライン)にコーナー処理を適用し、`corner_radius_mm`(最小5mm)を反映してからスイープする |
| ベースパッチとフランジの境界(折り目)フィレット | `AddNewFilletBiTangent` | 2スキン(ベースパッチ/フランジパッチ)間のバイタンジェントフィレット。`bend_radius_mm`(§4.2、未確定)を半径として使用 |
| フランジ幅のローカル膨らみ(ボス相当) | `AddNewExtrapolLength` / `AddNewOffset` | 境界曲線の締結点近傍区間のみをローカルに拡張・オフセットして幅変調を作る |
| ベース+フランジの結合 | `AddNewJoin` | 複数パッチを1つの連続した中立面サーフェスへスティッチ |

`AddNewSweepCircle`/`AddNewSweepConic`/`AddNewLoft`はこの用途では不要と判断(直線プロファイル+コーナー処理で十分)。`AddNewBlend`は接線連続ブレンドで実際の板金曲げ形状(一定半径フィレット)とは異なるため、折り目には`AddNewFilletBiTangent`を優先する。

具体的な引数構造(Reference/VARIANT配列の渡し方等)はPhase 1着手時に個別のインターフェースページ(`interface_HybridShapeFactory_27734.htm`等)で確認する。

## 6. Phaseロードマップ

- **Phase 0 (設計確定)**: §3の5クラスの閾値・オフセット許容量を実データの角度分布と照合して確定。§4のフランジ配置ルール(θと境界辺の対応関係、幅変調の振幅レンジ)をユーザーレビューを受けて確定。GSD側で使うCATIA V5 Automationコマンド(Sweep/Fill/Blend等)を調査。**完了**。
- **Phase 1 (最小PoC)**: `parallel_same_offset`クラスを対象に、中立面(締結点同士を面でつなぐメイン形状)を生成。GSDでの中立面生成→`joints.json`自動生成までの通し実行を確認。**完了**(§6.1/6.2参照。実機で15/15の頑健性検証済み)。フランジ補強は§6.11〜6.15で実装済みだが、**2026-08-07にユーザー方針転換により一時無効化**(§6.16)——学習データとしてメイン形状の生成そのものを優先するため。コードは凍結(削除ではない)、`include_flanges=True`で再有効化可能。

### 6.2 実機デバッグで判明した非自明な知見(要記録)

- **AppendHybridShape必須**: `AddNewXxx`で作った形状は`HybridBody.AppendHybridShape()`で明示的にツリー登録しないと、`part.Update()`が成功してもSTP出力が空になる。例外は出ない(静かに空ジオメトリを吐く)ため、初回はこれで丸1回ハマった。
- **AddNewFilletBiTangentの向き引数は曲げごとに反転する**: 2曲げジョグの1曲げ目(flat1-riser)は`iOrientation1/2=-1,-1`、2曲げ目(riser-flat2)は`1,1`でしかUpdateが通らなかった。他の全組み合わせは失敗。他classへ展開する際は都度グリッドサーチで確認要。
- **AddNewFilletBiTangentは`iSupportsTrimMode=1`が必須**: 0のままだと隣接パッチがフィレット領域と重複したまま残り、後続のJoinがUpdate失敗する。
- **AddNewSweepLineは調査を断念**: `SetLength`/`SetAngle`/`SetFirstLengthLaw`/`SetAngularLaw`(lawType 0/1/2/3全試行)のどの組み合わせでもUpdate失敗(無設定でも失敗)。90度固定フランジなら角度法則機構自体が不要なので、フランジ4隅を解析的に計算して`rect_fill`で作る方式に切り替えて解決した。非90度フランジが必要になったら再調査。
- **AddNewJoinは要素の並べ方(木構造)に強く依存する**: 7要素を単純に左から順にpairwise foldすると、要素の組み合わせに関わらず必ずUpdate失敗した。隣接する(境界を共有する)パーツ同士を先に小さくグループ化してJoinし、グループ同士を最後に合成する木構造にしたところ一発で成功した。この発見にたどり着くまでに最も時間がかかった。

実行: `cd synthetic_generator && python -m pytest -q` で20件、`cd annotation_tool && python -m pytest -q` で58件(スキーマ変更含む)がいずれも通過。実機生成: seed=7で`SYN_parallel_same_offset_0001〜0005`の5部品をSTP(各約22KB、実サーフェスエンティティ含む)+`joints.json`まで通しで生成成功。

### 6.3 余肉削減(材料最小化)の設計方針とPhase 1.5の新設(2026-08-03追加)

ユーザーからの実務知見: 板金設計では「余肉削減」(剛性・強度に寄与しない部分を削る)が前提。締結点が同一平面上にある場合、各点に必要な最小半径R(例: R25)の円2つと、それに外接する2本の接線で囲まれた領域(2円の凸包=長円/スタジアム形状)が構造上必要な最小材料であり、それ以外は余肉。ただしフランジやビードなど剛性・強度に必要な構造は、その領域からはみ出していても余肉とはみなさない。

この原則は同一平面2点に限らず一般化できる: 1つの面に締結点が1つしかない場合(`parallel_same_offset`のflat1/flat2等)は半径R一つ分、同一面にN点ある場合はN円の凸包が必要最小領域になる。

**Phase配置の決定**: 現行Phase 1(基本構築、完了)とPhase 2(効果測定ゲート)の間に**Phase 1.5: 余肉削減**を新設する。理由はPhase 2のゲート判定(合成データが実データ評価を悪化させないか)は形状のリアリズムに依存するため、矩形パネルのまま検証すると後で形状を直した際に再検証が必要になり手戻りになる。

**ハイブリッド方針(ユーザー確定)**: Phase 1.5でCATIA側に正確な長円(スタジアム)トリムを実装する前に、まず**余肉が出にくいラフな構造を今から作る**。具体的には`templates/parallel_same_offset.py`の`panel_width_mm`算出を、無関係な締結点間走行距離(`lateral`)基準から、新設した`min_bearing_radius_mm`(締結点周りの構造上必要な最小半径、R15〜30mmでサンプリング、ユーザー例のR25を含む)基準に変更した — `panel_width_mm ≈ 2×min_bearing_radius_mm×1.05〜1.25`。正確な円弧トリムはPhase 1.5でCATIA側に実装する(円/円弧のGSD API調査が新たに必要、Fillet/Joinで行ったのと同様のグリッドサーチが要る見込み)。

**頑健性検証(2026-08-03)**: 新しいサイジングロジックで、seed=100〜114の15部品を実機バッチ生成し15/15成功(`PartMaker\synthetic_parts\_robustness_batch\`)。多様な乱数パラメータ(オフセット・走行距離・板厚・軸受半径・フランジ高さ・コーナーR・曲げR)でも既存のフィレット向き(-1,-1/1,1)・グループ化Joinツリーの構造が崩れないことを確認。

### 6.6 メイン形状(ジョグ)の角度・R可変化 — §6.5の訂正(2026-08-04)

ユーザーから訂正: §6.5で角度可変化を適用すべきだったのはフランジではなく、**締結点同士をつなぐメイン形状(ジョグ)** だった。フランジは引き続き基本90度で正しい。実務では、メイン形状は面同士の角度をできるだけ平行に近づけ(=鋭い直角ではなく緩やかな遷移)、折れ目のRをできるだけ大きく取る(小部品でもR40〜50まであり得る)ほうが剛性・応力の観点で望ましい。ただし締結点周りの必要最小半径(`min_bearing_radius_mm`)は侵せないため、角度とRの2変数での実行可能性を確保する必要がある。今回は自動生成のため特定の意図(最適化)は持たせず、パラメータにランダム性を持たせて幾何的に成立する形状であればよい、との方針。

**実装**:

- `templates/parallel_same_offset.py`に`jog_ramp_extent_mm`を追加。ジョグの折れを水平方向にどれだけの距離をかけて緩やかに遷移させるかを表す。サンプリング上限は`lateral - 2*min_bearing_radius_mm`(締結点周りの必要最小半径を両端で確保した残り)に構造的に制限されるため、**棄却・リトライなしで常に成立する**設計にした。`jog_ramp_extent_mm=0`は従来の垂直リザー(直角2曲げ)に自然に退化する。
- `reinforcement.py`の`bend_radius_mm`を板厚比例(旧: 板厚×1〜3倍)から独立なR3〜50mmのサンプリングに変更(`BEND_RADIUS_RANGE_MM`)。
- `gsd_build.py`: `_panel_corners`をrun0側/run1側で異なる高さを取れるよう一般化(平坦パネルとランプの両方を1関数で表現)。`build_parallel_same_offset`で折れ目Rを隣接パネル(flat1長・ランプ長・flat2長)の0.8倍を超えないようクランプしてから`AddNewFilletBiTangent`に渡す(物理的に破綻しないようにするため)。

**実機検証**: ランプ・大R込みの新ジオメトリでもフィレット向き(-1,-1/1,1)は崩れず、ramp_extent=0〜79mm・bend_radius=4〜49mmの範囲で20/20成功。ユーザー例のR40〜50にも到達することを確認。

### 6.7 「Rが浮く」問題の修正: エッジフィレット方式への切り替え(2026-08-06)

ユーザー報告: §6.6の実装後、生成物の多くで形状が破綻していた。Rが大きいと`AddNewFilletBiTangent`のブリッジ面がトリムされたパネル残余部分と接触せず「浮いた」状態になり、CATIAの`Update()`は成功するのに実際には形状が繋がっていなかった。

**原因**: `AddNewFilletBiTangent`は2枚の未結合サーフェスをRで橋渡しする方式(SS6参照)。Rが対象パネルの寸法に対して大きすぎると、トリム後の橋渡し面が実際のパネル残余部分に届かず接触しないケースが生じる。§6.6で追加した0.8倍クランプは、この問題を統計的に減らすだけで根本解決になっていなかった。

**ユーザー提案の修正方針(採用)**: Rによる決定論的な事前クランプではなく、構築の順序そのものを変える。

1. flat1・ランプ・flat2をシャープな角のまま**先に完全結合**する(平面同士の結合はRに依存せず常に確実 — 既に実証済みのJoinパターン)。
2. 結合済みの1つのシェルに対して、実際のエッジ(`Selection.Search("Topology.CGMEdge,sel")`で列挙し、解析的に計算済みの折れ目中点への最短距離で目的のエッジを特定)に、`part.ShapeFactory.AddNewSurfaceEdgeFilletWithConstantRadius(edge, propagMode, radius)`(MecMod/PartInterfaces系、GSDのHybridShapeFactoryとは別系統)を**順番に**適用する。

この方式では、フィレットは既に位相的に正しい(繋がっている)シェルの実エッジを丸めるだけなので、「浮いた」面が原理的に発生しない。

**実機検証**:
- `Selection.Item2(i).Value`を`part.CreateReferenceFromObject`に渡すとエラーになったが、`Selection.Item2(i).Reference`は直接有効なReferenceを返す(新知見)。
- R47.6mm(旧方式で浮いていたと推測される値)を含む複数ケースで、STP出力が単一の`OPEN_SHELL`(完全に接続された1つの殻)になることを確認。
- 25部品バッチ(seed=400〜424)で19/25が成功し、**成功した19件全てが単一シェル**(破綻なし)。失敗した6件はいずれもランプがほぼゼロ(垂直に近い)かつRが大きい組み合わせで、これは本当に材料が足りない幾何学的に無理な要求であり、**明示的な例外として失敗する**(旧方式のような「サイレントな破綻」ではなくなった)。
- ユーザー指示により、Rの決定論的な事前クランプ(§6.6で導入した0.8倍ルール)は撤去した。無理な組み合わせは失敗させてよい、という方針。

**まだ対応していない点**: `generate_batch`は1部品でも失敗すると全体が止まる設計のまま。本番バッチ運用では失敗をスキップ/リトライする仕組みが必要になりそうだが、これは今回のジオメトリ修正とは別の話として、着手前にユーザー確認が必要。

### 6.8 締結点の必要最小半径の未考慮を修正(必須要件、2026-08-06)

ユーザー報告: 生成データの一部で締結点の必要最小半径(`min_bearing_radius_mm`)が加味されていなかった。調査の結果、**2つの独立した不備**が見つかった。

1. **ジョグ折れ目のフィレットが締結点側に食い込む**: `jog_ramp_extent_mm`のサンプリング(§3.1/templates)は、シャープな角の位置が締結点から`min_bearing_radius_mm`以上離れることは保証していたが、実際にRを付けてフィレットにすると、理論上のシャープな角より手前(`radius_mm * tan(折れ角/2)`だけ手前)からフィレットが始まる。この後退量を全く考慮していなかったため、Rが大きい場合に丸めた部分が締結点の必要最小半径の内側まで食い込みうる状態だった。
2. **フランジ側に平坦な余白が一切確保されていなかった**: フランジはこれまで締結点そのものの位置(run=0 / run=run_length)から直接立ち上がっていた。締結点を中心とした円全体が平坦材料で覆われている必要があるのに、フランジ側には片側の余白が最初から存在しなかった。

**修正**(`gsd_build.py`):

- `_fold_tangent_length_mm(offset_mm, ramp_extent_mm, radius_mm)`を新設。フィレットの後退量を`radius_mm * tan(alpha/2)`で計算する(alpha = atan2(offset_mm, ramp_extent_mm) = ランプの傾き角)。ramp_extent=0(垂直リザー)のとき後退量はRそのものに一致する。
- `build_parallel_same_offset`の冒頭(CATIA呼び出し前)で、後退後の残り平坦長が`min_bearing_radius_mm`を下回る場合は`ValueError`を送出し、構築を試みない(Python側の事前チェック、CATIA呼び出しゼロで高速に判定できる)。
- flat1/flat2の始点・終点を締結点の位置(run=0 / run_length)ではなく、そこから`min_bearing_radius_mm`分外側(run=-min_bearing_radius_mm / run_length+min_bearing_radius_mm)に変更し、フランジ側にも必要な平坦余白を確保。フランジはこの新しい外側エッジから立ち上がる。

**検証**: 以前CATIAのUpdateが失敗していた6ケース(seed=406/412/414/417/418/424)は、いずれも新しい事前チェックにより**0.00秒**(CATIA呼び出しなし)で`ValueError`として検出されることを確認。さらに重要な発見として、**以前「成功」と判定されていたseed=401(ramp=69.0, R=27.8)も、実際には必要最小半径違反だったことが新チェックで判明**した — 旧コードでは締結点保護の検証が一切なかったため、CATIA的に「繋がってはいる」が構造要件を満たさない形状を静かに生成していたことになる。

新しいseed=500〜524の25部品バッチでは8/25(32%)が成立し、17件は事前チェックでの`ValueError`、**CATIA呼び出し自体の失敗は0件**(事前チェックがCATIAでの成否を完全に予測できている)。成功した8件は全て単一OPEN_SHELL(接続良好)を確認。成立率が§6.7時点(19/25=76%)より下がったのは、`offset_mm`(最大60mm)や`bend_radius_mm`(最大50mm)が`min_bearing_radius_mm`(15〜30mm)と独立にサンプリングされているため。

### 6.9 歩留まり改善(2026-08-06)

ユーザー要望: 部品のランダム性は維持したまま歩留まりを改善する。方針: `bend_radius_mm`を独立サンプリングするのをやめ、既にサンプリング済みのジョグ幾何(ランプ長・オフセット・必要最小半径)から**実行可能な範囲を計算し、その範囲内でランダムサンプリング**する(構造的に常に成立、棄却・リトライ不要)。

**実装**(`templates/parallel_same_offset.py`):

- `fold_tangent_length_mm`を`classify.py`(依存関係のない共有モジュール)に移動し、`templates`と`gsd_build`の両方から同じ式を使えるようにした(循環importを避けるため)。
- `bend_radius_mm`を`reinforcement.py`から`TwoJointSpec`(templates側)へ移動。ジョグ幾何が確定した直後に、`x_start`(締結点からジョグ折れ目までの距離)と`bearing_radius`から実行可能上限を逆算し、`rng.uniform(0, max_bend_radius)`でサンプリングする。

**追加で見つかった根本原因(2件)**:

1. **`lateral`(締結点間距離)と`bearing_radius`が独立サンプリングされていたため、フィレット半径ゼロでも成立しない組み合わせが存在した**: `lateral`の下限(20mm)が`bearing_radius`の上限(30mm)の2倍(60mm)より小さく、両端の必要最小半径を確保できないケースがあった。回帰テストで実際に検出。修正: `bearing_radius`を先にサンプリングし、`lateral`の下限を`max(20mm, 2*bearing_radius)`に連動させた。
2. **フィレット半径が及ぼす幅方向(パネル幅)への影響を考慮していなかった**: 実機で1件、`bend_radius`(33.8mm)が`half_width`(32.9mm)とほぼ同じ大きさになりCATIAのUpdateが失敗するケースを発見。修正: `bend_radius`の実行可能上限に`0.9*half_width`のクランプを追加。

**検証結果**: seed=700〜739の40部品バッチで**40/40成立**(事前チェック棄却0件、CATIA失敗0件)、全件が単一OPEN_SHELL(接続良好)。`bend_radius_mm`は0〜約48mmまで実際に分布し、ランダム性は維持されている。

**検証中に見つかった別件(未対応、今回のスコープ外)**: 40件バッチのうち1件(seed=701)でSTPが空(旧来のAppendHybridShape欠落と同じ症状)になったが、同じseedを単体で再実行すると正常に生成された(271行、シェル1件)。ジオメトリ固有のバグではなく、長時間のバッチ実行によるCATIAセッション側の一時的な不具合の可能性が高い。今回の依頼(歩留まり改善)の範囲外のため、ユーザーに報告のみで深追いはしていない。

### 6.10 アボート時のクリーンアップ(2026-08-06)

ユーザー指摘: アボートした部品がそのままCATPartとして残ると、学習材料を選別する際の邪魔になる。原因: `export_stp`(ドキュメントを閉じてファイルを書き出す処理)は構築の最後にしか呼ばれないため、それより前の段階(Join/エッジフィレット等)で例外が起きると、開いたドキュメントが保存されないまま残り続けていた。

**検証**: 意図的にCATIAレベルの失敗(幅方向のクランプを迂回したbend_radius)を発生させ、(1)出力ファイルが残らないこと、(2)3回連続で失敗させてもCATIA側の開いたドキュメント数が増えないこと(リークなし)を確認。なお検証中に見つかった、本修正以前のテスト実行に由来する開いたままの未保存ドキュメント十数個、および蓄積していたデバッグ用出力ディレクトリ(`_robustness_batch*`等)は削除済み。

### 6.15 フランジ配置の方針転換: θ厳密一致から「締結点を結ぶ線に平行」へ(2026-08-06、§6.11 Step3を置き換え)

**ユーザー指摘**: θ(`reinforcement_direction_deg`)への厳密な方向一致は、離散的な辺の選択肢しかない以上不可能(連続的なθに対して選べる辺は有限個)。方針転換して、どちらかの締結点に荷重がかかった時に耐える方向でフランジを立てたい。必然的に締結点を結んだ線に平行なフランジになる(梁のフランジが梁のスパンに平行に走ることで、正確な荷重方向によらず横方向の曲げに広く効くのと同じ原理)。

**確定事項(ユーザー回答)**:
- θは今後、フランジの方向選択には使用しない(常に締結点を結ぶ線 = 走行方向に平行)。`reinforcement_direction_deg`自体はreinforcement.py側にサンプリングとして残すが、gsd_build.pyでは未使用の付随値になる。
- フランジは片側のみ(幅方向+half_width側の側辺、シンプルさ優先。対称両側は不採用)。

これにより§6.11で計画していたStep3(θに応じた走行方向端部/幅方向側辺の切り替え、置き換え方式)は**廃止**。「常に幅方向側辺(片側)」という単一ルールに置き換わった。

**実装に伴い新たに発覚した2つの派生課題と対応**:

1. **コーナーリリーフの必要性**: 新配置ではフランジ根本の折れ(小径R)が、メイン形状の折れ(fold1/fold2、大径Rもあり得る)と同じ角(頂点)を共有するようになった(旧・走行方向端配置では離れた辺にあり無関係だった)。両方に独立してエッジフィレットを当てると、フィレット領域が競合し、CATIA側の`Update`が失敗するか、あるいは(フィレット順序を反転させた場合)**エラーなく幾何が縮退する**(丸みがつかず鋭い折れ目のまま描画される)ことを、CATIAビューワのスクリーンショットを使った複数パターンの目視検証で確認した。フィレット順序の反転は「エラーは消えるが形状が歪になる」ため不採用とし、代わりに実務のシートメタルで一般的な**コーナーリリーフ**(2つの曲げ加工が交差する角では、一方の曲げをその角の手前で止めて干渉を避ける)を採用: フランジの走行方向の辺を、メイン折れのフィレット後退量(`tangent_length_for_bend_angle_rad`で計算、ジョグ側の事前チェックで使うのと同じ値)ぶんだけ角の手前で止める。構築順序(メイン折れ→フランジ根本、§6.11確定順序)は変更しない。中立面R最小4mm(必須制約)を含む複数のR・ランプ角の組み合わせ、および実際の5要素フルパイプラインで、Update成功・目視ともクリーンであることを確認済み。
   - なお目視検証の過程で、パーツツリーに残っていた構築用の点・直線(補助形状)がスクリーンショット上で面と重なって「縮退しているように見える」誤検知が一度発生した。実際の面ジオメトリの健全性を確認する際は、これら補助形状を非表示化してから再撮影する必要がある(構築ロジック自体には影響なし、目視検証手順上の注意点)。
2. **幅方向余白不足による歩留まり低下**: `panel_width_mm`は元々「締結点の必要最小半径の2.05〜2.5倍」という、旧配置(フランジは走行方向端)向けのサイジングだった。新配置ではフランジ根本の折れが幅方向の外側から中心(締結点)に向かって侵入してくるため、`half_width`に対する実質的な余白がほぼゼロで、2000サンプルの定量調査で77%が新設の幅方向事前チェックでInfeasible判定された(不足分: 中央値1.3mm、上位10%で2.9mm以上、最大8.9mm)。`templates/parallel_same_offset.py`に`FLANGE_WIDTH_SAFETY_MARGIN_MM = 12.0`を新設し、`panel_width`に固定加算マージン(`+2*12=24mm`)を上乗せするよう修正。この12mmはreinforcement.pyの現在のサンプリング範囲(板厚1.0〜2.5mm・`FLANGE_BEND_RADIUS_RATIO_CAP`=3倍・斜めフランジ最大120度)から逆算した理論上限で、5000サンプルの再検証で幅方向Infeasibleは0%になった。

**実装箇所**:
- `gsd_build.py`: `build_parallel_same_offset`のフランジ構築ロジックを、走行方向端部の辺(`flat1_corners[0]/[1]`, `flat2_corners[2]/[3]`)から、幅方向+half_width側の側辺(`flat1_corners[1]`→`flange1_relieved`, `flange2_relieved`→`flat2_corners[2]`)に変更。`outward_tangent`は両フランジとも`frame.width_dir`で共通。`flange_margin`は走行方向のフィレット後退量の上乗せが不要になったため`min_bearing_radius_mm`のみに簡素化。幅方向の新規事前チェック(`half_width - flange_tangent_length >= min_bearing_radius_mm`)を追加。
- `templates/parallel_same_offset.py`: `FLANGE_WIDTH_SAFETY_MARGIN_MM`定数を新設し、`panel_width`計算式に反映。

**検証**: 実際の生産コード経路(`build_parallel_same_offset`)で40部品バッチ(seed=2000)を実行し、**35/40成功(87.5%)・CATIA呼び出し自体の失敗は0件**・成功した35件は全て単一シェル。コーナーリリーフ導入前は同条件で1/20(5%)成功だった(幅方向Infeasibleが大半、かつ稀にCATIA Update失敗もあり)。

### 6.17 Phase 1.5実装: 締結点周りの円弧トリム(2026-08-07)

**円・円弧APIのグリッドサーチ**: `HybridShapeFactory`の円・円弧作成APIは今回初めて使用した(Fillet/Join同様、未検証APIのため実機で調査)。

**幾何構築**: 締結点(円中心)から遠端(ランプ側の直線境界2点)への外接線の接点を解析的に計算(`gsd_build._tangent_arc_boundary`、標準的な「点から円への接線」公式)。境界は`line(corner_a,corner_b) → line(corner_b,tangent_b) → arc(tangent_b→tangent_a, sweep_deg) → line(tangent_a,corner_a)`の4本の閉ループ。`sweep_deg`(円の裏側=遠端から離れた側を通る弧の掃引角度)は対称性から`(360-2K) mod 360`(K=遠端への視線角+接線半角)で解析的に導出し、単体テスト(`test_gsd_build_geometry.py`、真の接線条件の直交性チェック含む)で検証。

**検証手法の教訓**: スクリーンショットは今回のジオメトリスケール(半径15〜30mm程度)では既定カメラが遠すぎて写らず、目視検証が機能しなかった。代わりに`spa.GetMeasurable(faceRef).Area`(CATIA既定はSI単位=m²、mm²換算には×1e6が必要)と、円弧を多数の線分で近似したシューレース公式による独立計算を突き合わせ、5〜6桁の精度で一致することを確認 — スクリーンショットより遥かに確実で、今後同種の小スケール形状検証にも応用できる。

**実装範囲(意図的な単純化)**: `include_flanges=True`のときは、フランジのガイド辺が円弧境界にどう接続すべきか未検討のため、Phase 1.5トリムは適用せず旧来の矩形+`flange_margin`のままにした(§6.16でフランジは既定無効化済みのため、現状はトリムが常に有効なパスになる)。フランジ復活時にトリムとの整合を取るのは別課題として残す。

**検証**: 実際の生産コード経路で30部品バッチ(seed=3000)を実行し、**18/30成功・CATIA呼び出し自体の失敗は0件**・成功した18件は全て単一シェル。生成されたCATPartを目視確認したところ、締結点ごとの円形の座面(ベアリングゾーン)がジョグの折れ目に向かって滑らかにすぼまる、意図通りの「ドッグボーン」形状になっていることを確認した。

### 6.19 §6.17トリム形状の訂正: 「ドッグボーン」から真の「長円(スタジアム)」へ(2026-08-07)

**ユーザー指摘**: §6.17の実装(生成物を本番ディレクトリで確認したユーザーから)は、長円ではなく「長方形の左右に三角形を2つつけ、その三角の端を締結点の必要最小平面に沿ってRを取ったような形状」になっていた。理想形状は長円(スタジアム: 平行な直線2本+半円キャップ2つ)。

**原因**: `_tangent_arc_boundary`の遠端コーナー(corner_a/corner_b)に、当時`spec.panel_width_mm/2`(フランジ用に余裕を持たせた広いサンプリング幅、§6.15の`FLANGE_WIDTH_SAFETY_MARGIN_MM`込み)を渡していた。半径(min_bearing_radius_mm)よりこの半幅が大きいと、接線は遠端コーナーに向かって斜めに伸び、円周のごく一部だけを切り取る小さな弧になる(半幅が半径よりずっと大きいケースほど、弧は退化してほぼ点=三角形の先端の小さなRにしか見えなくなる)。これは「凸包」の定義としては正しいが、視覚的に長円には見えない。

**修正**: `half_width`をtrim経路(`include_flanges=False`)のときだけ`spec.min_bearing_radius_mm`(=円の半径そのもの)に変更(`include_flanges=True`のときは従来通り`panel_width_mm/2`)。`_tangent_arc_boundary`は`half_width==radius`のとき解析的に厳密退化することを事前に確認した: 接点が必ず`(0, ±radius)`(=締結点の真横、run=0の位置)になり、接線は幅方向±radiusの完全な平行線に、掃引角は厳密に180度(=半円)になる。この退化ケースの証明は数値実験でも裏付け(`_tangent_arc_boundary`をfar_distance=5〜100の広い範囲で試し、常にsweep=180.000000、接点run座標=0を確認)。ランプも同じ`half_width`を使うため、flat1・ランプ・flat2の境界幅が一致し段差なく結合される。コード変更は`half_width`の定義1箇所のみ(`trimmed_end_panel`自体や`_tangent_arc_boundary`は無変更 — 一般的な凸包構築ロジックがこの特殊ケースを正しく含んでいたため)。

**検証**: 実際の生産コード経路で30部品バッチ(seed=4000)を実行し、**12/30成功・CATIA呼び出し自体の失敗は0件**・全件単一シェル(半幅が縮んだ分、ジョグ折れRとの整合性チェックがより厳しくなり、§6.17時点の18/30から低下したが許容範囲)。生成物を目視確認し、平行な直線側辺+両端の半円キャップからなる真の長円(スタジアム)形状になっていることを確認した。本番バッチ`parallel_same_offset_batch1`をこの修正版で再生成(40/40成功・全件単一シェル)。

### 6.20 方針転換: クラス横展開より先に「任意法線・任意位置」でのメイン形状生成を優先(2026-08-10)

**ユーザー方針**: これまでのPhase 3計画(§6のPhase一覧参照)は「効果測定(Phase 2)後、5クラスへ横展開(フランジ主体のまま)」だったが、優先順位を転換する。フランジ・トリムより先に、**任意の法線の組み合わせ・任意の位置の組み合わせで、締結点2点を面でつなぐメイン形状の生成そのものを成功させる**ことを最優先にする。現状の`gsd_build._jog_frame`は`n1 ≈ n2`(法線がほぼ一致、`parallel_same`クラスのみ)を暗黙に前提しており、それ以外のクラス(`parallel_opposite`/`orthogonal`/`oblique`)では正しい形状にならない。

**幾何設計(検討結果、実装前にユーザー確認予定)**:

現行`_jog_frame`は、`n1`(締結点1の法線)を単一の基準法線として全体を構築しており、flat1もflat2も同じ`n1`に垂直な平面上にあることを前提にしている(`n1≈n2`のときのみ正しい)。一般化のポイントは、**全ての折れ目(fold line)を単一の共通方向`w`に平行にする**という制約を維持したまま、`n1`と`n2`が異なる場合にも対応することである:

- `w`は「flat1(法線`n1`)にもflat2(法線`n2`)にも直線の折れ目を許す」ためには`w⊥n1`かつ`w⊥n2`である必要がある。`n1`と`n2`が平行でない一般ケースでは、これを満たす方向は`w = normalize(n1 × n2)`の1つ(符号除く)に一意に決まる。
- `n1 ∥ n2`(現行の`parallel_same`クラス)のときは`n1×n2=0`で退化するため、現行`_jog_frame`と同じフォールバック(`w = normalize(n1 × tangential(p2-p1))`、すなわち締結点間の接平面内変位方向を使う)を維持する。両方退化する場合(法線一致かつ横方向変位ゼロ)は現行通りInfeasible。
- `w`が求まれば、`n1`と`n2`は共に`w`に垂直な単一の2D平面内に存在するので、両者のなす角度`θ = angle(n1, n2)`(0〜180度)だけ、その2D平面内で法線が回転すればよい。現行のflat1・ランプ・flat2という3ピース構成(fold1・fold2の2箇所)は、`θ=0`のとき(現行の`parallel_same_offset`)は「ランプの傾きだけ変化・法線は往復して元に戻る」構成だったが、一般化後は**fold1とfold2の折れ角が独立**になり(もう「往復」ではない)、それぞれの角度がその2D平面内の幾何(`p1`・`n1`・`p2`・`n2`の位置関係)から一意に解ける。

**未解決の設計判断(ユーザー確認したい点)**:

1. **横方向オフセット(`w`方向の変位)の扱い**: `w`は`n1`・`n2`だけから決まるため、`p2-p1`が`w`方向の成分を持つ場合(=2点が横にもズレている一般配置)、現行の「幅方向±half_widthの矩形/長円」だけでは繋がらない。案: 折れ目に沿って幅方向の中心線を線形にシフトさせる(パネルが台形状にわずかに捻れる)ことで吸収する。実装コストは中程度(`_panel_corners`を「run位置に応じて幅中心もシフトする」よう一般化する必要がある)。
2. **1回のランプで無理な角度になる場合の扱い**: `θ`が大きい(例: ほぼ直交・対向)場合、単一のランプ折れ角も大きくなる。過去の設計知見(メモリ参照: 剛性面では面同士をできるだけ平行に近づけ、1曲げあたり最大90度・目安45度)を踏まえると複数ランプへの分割が望ましいが、「まず成功させる」優先順位に照らし、**第一段階では単一ランプ(2箇所折れ)のまま許容し、角度分割は後続の改善タスクとする**のが妥当と考えている。
3. **フランジ・Phase 1.5トリムとの関係**: 今回の一般化はフランジ無効(`include_flanges=False`)経路のみを対象とする(§6.16の方針を継続)。Phase 1.5トリム(§6.17/6.19)も、まずは一般化した`_jog_frame`が正しく通ることを優先し、円弧トリムの整合は一般化後に再検証する。

### 6.21 §6.20実装: `_two_point_frame`/`build_general_two_point`(2026-08-10)

**幾何の実装**: `gsd_build.py`に`_two_point_frame`(共通幅方向`w`とローカル走行方向`u1`/`u2`)、`_end_panel_corners`(任意の`u`/`w`フレームでの平坦矩形)、`_ramp_fold_angles_rad`(ランプ中心線とu1/u2のなす角=各foldの折れ角)を追加。横方向オフセット(open decision #1)は、**ランプ自体を台形にする**ことで自動吸収する方式を採用: flat1/flat2はそれぞれ自分の点を中心とした矩形のまま(変更不要)、ランプの4隅を「flat1のランプ側辺(flat1_corners[2]/[3])」と「flat2のランプ側辺(flat2_corners[0]/[1])」を直接結んだ4点とするだけで、2直線が共にw方向に平行である限り幾何的に必ず平面になる(証明はテストで確認済み)ため、`_panel_corners`のような高さ補間式は不要だった。

**検証**: 純粋関数テスト19件追加(`n1=n2`退化ケースでの`_jog_frame`との厳密一致、直交法線での角度保存、反平行ケースの処理、一般ケースでのランプ平面性の解析証明、fold角度公式が既存の`alpha=atan2(offset,ramp_extent)`公式と厳密一致することの確認)。実機CATIAでも、直交法線+横方向オフセットありのケースで構築(join・fold1/fold2フィレット)が成功し、単一シェルでエクスポート、目視でも物理的に妥当なブラケット形状であることを確認した。

**発見した問題: 大角度での連続フィレットの数値的脆さ**: `build_general_two_point`を実装し、ランダムな法線・位置の組み合わせでバッチ検証したところ、Python側の事前チェック(タンジェント長・R>=4mm等)を全て満たしているにもかかわらず、CATIA側のUpdateが失敗するケースが一定数見つかった(fold1/fold2どちらを先にフィレットしても、2番目に当てた方が失敗する)。原因の切り分けのため、fold1・fold2の角度を独立制御できるテスト治具を作り、以下を体系的に検証した:

- fold1・fold2それぞれ30〜130度の総当たり(連続回転/ジグザグの両方の折れ方、計72通り) → **全て成功**
- 実際に失敗した具体的ケース(fold1=116.5度、fold2=120.8度)と同じ角度・同じ横方向オフセット(58.6mm)・同じランプ長で再構成 → **成功**(再現せず)
- 上記に加えてランダムな3D回転を6パターン適用 → **全て成功**(再現せず)
- 元の失敗ケース自体は、締結点2の位置を±0.5mmだけ揺らしても安定して失敗 → **摂動に対して頑健に失敗する**(数値的な際どい境界ではない)

つまり、系統的な角度閾値やオフセット閾値としては再現できない一方、元の具体的な配置は確実に(摂動を加えても)失敗する — 特定の3D配置に固有のCATIA側数値ソルバーの脆さであり、Python側の事前チェック式で予測するのは非現実的と判断した。

**採用した対応(ユーザー確認済み)**: `build_general_two_point`内で、2箇所のエッジフィレット(`edge_fillet`+`Update`)をtry/exceptで囲み、CATIA側の例外を捕捉して`ValueError`(Infeasible)に変換する。join等の他のステップで例外が出た場合は変換せずそのまま送出する(実バグを握りつぶさない方針は維持)。これにより`batch_generate.py`の既存skip-and-retry方針(§6.18)がそのまま機能する。

**検証**: ランダムな法線・位置のバッチ(25件)を実行し、元の失敗ケースが`ValueError`として正しく変換されることを確認した上で、**16/25成功(64%)・CATIA呼び出し自体の失敗は0件**・成功した16件は全て単一シェルを確認した。

**次のタスク**: `templates/`側のサンプリング(任意法線・任意位置をランダム生成する新テンプレートモジュール)と、feasibility事前チェックの仕上げ(現状`fold1_run_mm`/`fold2_run_mm`/`bend_radius_mm`は決め打ちでテストしており、`parallel_same_offset.py`のような「実行可能範囲内でのみサンプリングする」設計にはまだなっていない)。

### 6.22 `templates/general_two_point.py`実装(2026-08-10)

**設計**: `parallel_same_offset.py`と同じ「実行可能範囲を計算してからその中でサンプリングする」方針を、任意法線・任意位置ケースに一般化した新テンプレートモジュール。主な違い:

- 法線n1はランダムな単位ベクトル、n2はn1をランダムな軸まわりにランダムな角度(0〜180度)回転させたもの — 特定のconfiguration classに限定せず、5クラス全てが出現しうる分布にした(`parallel_same_offset.py`は`n1`をわずかにジッターさせるだけで`parallel_same_offset`クラス限定だった)。
- 締結点2の位置も、締結点1から見て完全にランダムな3D方向・距離(60〜200mm)。
- `fold1_run_mm`/`fold2_run_mm`(旧来の対称な`jog_ramp_extent_mm`分割の代わり)は、まず生成に十分な余裕を持った範囲(`bearing_radius+10〜80mm`)で独立にサンプリングし、その後**実際にflat1/flat2のランプ側辺を計算してfold1・fold2の折れ角を求め**(一般ケースでは`parallel_same_offset`のoffsetのような単純な閉じた式が無いため)、そこから`bend_radius_mm`の実行可能上限(締結点のbearing radius保護・ランプ上でのフィレット重なり回避・パネル幅0.9倍以内の3条件)を逆算してサンプリングする。中立面R最小4mmの制約下で実行可能上限が4mm未満の場合はあえて4mmを返す設計は`parallel_same_offset.py`と同じ。

**検証**: 単体テスト4件追加(複数configuration classの出現確認、製造制約レンジの遵守、bend_radiusが独立再計算した実行可能上限に収まるか強制最小値になっているかの照合、決定論性)。実際の生産コード経路(`build_general_two_point`)で40部品バッチを実行し、**31/40成功(77.5%)・CATIA呼び出し自体の失敗は0件**・成功した31件は全て単一シェル。configuration class分布はoblique 31件・parallel_same_offset 6件・orthogonal 2件・parallel_opposite 1件と、意図通り複数クラスが自然に出現した。目視でも2件確認し、いずれも物理的に妥当な(自己交差やねじれのない)折れ曲がりブラケット形状であることを確認した。

### 6.23 `batch_generate.py`の一般ケース対応と本番バッチ生成(2026-08-10)

**実装**: `generate_batch`(parallel_same_offset専用)とは別に`generate_general_batch`を新設(`GeneralPartBuilder`Protocol・`GeneratedGeneralPartRecord`も新設)。既存の`generate_batch`と同じskip-and-retry方針(ValueErrorはスキップ・それ以外の例外はバッチ全体を中断)をそのまま踏襲。`build_parallel_same_offset`(spec+reinforcement引数)と`build_general_two_point`(point1/point2+個別キーワード引数)は引数の形が異なるため、共通の抽象化は作らず素直に別関数にした。テスト4件追加(オーケストレーション検証、決定論性、skip-and-retry)。

### 6.24 不要な2曲げの解消と面干渉の事前チェック(2026-08-21)

**発端**: バッチ結果のSTPをPNGコンタクトシートにレンダリングする`tools/render_stp.py`(pythonOCCでテッセレーション→matplotlibでランバート陰影、40件3秒)を用意して全件を一覧で目視できるようにしたところ、ユーザーが2つの問題を指摘した: (1) 曲げが1回でいいのに2回折っている形状がある、(2) 曲げた結果、面同士が交差して干渉している形状がある。

**問題1(不要な2曲げ)の原因と定量**: `build_general_two_point`は「flat1+ランプ+flat2」の3ピース固定で、折れ目が必ず2本できる(法線が平行なジョグ由来の構成をそのまま一般化したため)。法線が交わる一般ケースでは2平面の交線で1回曲げれば足りる。3000サンプルの実測で、既存の事前チェックを通った2958件のうち**962件(32.5%)は交線が両締結点の前方にあり、bearing radius + フィレット接線長の余裕も満たす=単曲げで作れる**ケースだった。

**ユーザー方針(2026-08-21)**: 2曲げで生成できているケースを失いたくないので保守的に。「無駄な曲げ量」= (fold1の折れ角 + fold2の折れ角) − 正味の折れ角θ が大きい極端なケースだけを単曲げに置き換える(excess=0なら2つの折れが同方向にθを分担しているだけで妥当な2曲げ部品、大きいほど行き過ぎて戻るS字=明らかに余計な曲げ)。単曲げ可能ケースのexcess中央値は43度で、閾値30度なら37%、20度なら42%、40度なら32%が置き換わる。**excess > 30度**を採用した。

**実装**: `classify.py`に`SingleFoldLayout`/`single_fold_layout()`を新設(サンプリング側と構築側の両方から使えるよう、既存の`two_point_frame`等と同じ配置方針)。`build_general_two_point`は、2曲げ用のfold角を計算した直後に`single_fold_layout`を呼び、Noneでなければパネル2枚+折れ目1本で構築する。join〜フィレット〜エクスポートは単曲げ/2曲げで共通なので`_assemble_general_two_point`に括り出した(フィレットは`fold_mids`のループになり、CATIA側の脆さに対するValueError変換(§6.21)もそのまま共通化されている)。

- **幾何の核心**: 交線Lは必ず共通幅方向wに平行になる。したがって両パネルをw方向に共通の幅中心cm=(c1+c2)/2までずらし、半幅を`half_width + |Δw|/2`に広げれば、**flat1の折れ目側の辺とflat2の折れ目側の辺が厳密に一致する**(単一シェルになる条件)。広げても各締結点の幅方向余白は元の`half_width`のまま保たれる(どちらもテストで確認済み)。
- 単曲げでは幅方向オフセットΔwをランプの台形で吸収できない(2曲げ経路との構造的な差)ため、パネルを広げすぎないよう`SINGLE_FOLD_MAX_LATERAL_RATIO = 3.0`(幅の膨張は2.5倍以内)で上限を置き、超える場合は2曲げに任せる。
- `fold1_run_mm`/`fold2_run_mm`は単曲げ経路では使わない(折れ目の位置が交線として幾何的に決まるため)。

**問題2(面干渉)の原因と定量**: wに垂直な断面で見ると形状はflat1→ランプ→flat2の3セグメント折れ線になる。既存の事前チェック3つ(R≥4mm、接線長がbearing radiusを侵さない、2つのフィレットがランプ上で重ならない)は**どれも隣接する折れ目まわりしか見ておらず、非隣接のflat1-flat2の交差を誰も見ていなかった**。実測では2958件中517件が断面上で交差していたが、**うち333件は幅方向にすれ違っているだけで3Dでは干渉していない** — 幅レンジの重なり判定(|Δw| < 2*half_width)を入れないと交差の2/3を過剰に弾くことになる。実際に干渉しているのは**184件(6.2%)**、加えて距離5mm未満のニアミスが47件(1.6%)。

**実装**: `classify.flat_panels_clearance_mm()`(断面2Dでのflat1-flat2の最小距離、幅方向にすれ違っていればinfを返す)を新設し、`build_general_two_point`の2曲げ経路の事前チェック群に`clearance < MIN_PANEL_CLEARANCE_MM (=5.0)`でInfeasibleを追加。全ての生成経路がこの関数を通るのでここ1箇所でよい。既存のskip-and-retry(§6.18)がそのまま吸収する。単曲げ経路は断面が2セグメントになるので原理的に干渉せず、チェック不要。

**検証**:
- 純粋関数テスト6件追加(折れ目の辺の厳密一致、幅を広げてもbearing余白が保たれること、法線平行/excess不足/横オフセット過大での単曲げ拒否、断面交差の検出と幅方向すれ違いの除外、素直なジョグでの正のクリアランス)。CATIA非依存で全57件パス。
- **実際のproductionコードパス**(`build_general_two_point`を、CATIA呼び出し部分`_assemble_general_two_point`だけスタブに差し替えて実行)で3000サンプルをdry-run: 単曲げ**13.2%**、面干渉による棄却158件、**受理された2曲げ形状の残存干渉0件**、歩留まり98.6%→93.6%(`max_attempts_per_part=50`なので影響なし)。
- `synthetic_parts/general_two_point_batch2/`にseed=2000(batch1と同一シード)で40部品を再生成、**40/40成功**。configuration class分布はoblique 23・parallel_same_offset 14・orthogonal 3。
- 生成物のSTPから円筒面(=フィレット=曲げ)の数を直接数えて実測: **batch1は40件すべて2曲げ、batch2は単曲げ5件(0006/0027/0035/0037/0038)・2曲げ35件**(12.5%、dry-runの13.2%と一致)。単曲げ5件を目視し、いずれも素直なL字ブラケットになっていることを確認した。

**検証手順上の注意点(記録)**: 生成された各部品が単曲げか2曲げかを、同じseedでrngストリームを再現して対応付けようとしたが**一致しない**。CATIA側の失敗(§6.21のフィレット脆弱ケース)でValueErrorが出るとdry-run側とストリームがずれ、以降の部品番号が食い違うため。生成物そのもの(STEPの円筒面数)を数えるのが正しい方法。
